# Архитектурный roadmap: масштабирование AI Gidromap

**Дата:** 2026-08-12
**Статус:** согласован, готов к декомпозиции на реализационные планы

## Контекст и ограничения

Проект сейчас: Next.js + Supabase, один регион (Акмолинская область), 28 гидропостов
зашиты прямо в `src/lib/akmolaMapData.ts`, sessions/rate-limiting чата — в
in-memory `Map` (сбрасываются при рестарте инстанса), ИИ-агент на DeepSeek с
бизнес-правилами строкой в system prompt, 3D-рельеф — локальный `.mbtiles`
файл на регион.

Ключевые вводные, определившие приоритеты ниже:

- **Горизонт:** первый клиент уже практически договорён (недели — 1-2 месяца). Не
  гипотетическое планирование — решения нужны быстро.
- **Первый клиент — SaaS или self-hosted, ещё не решено.** Оба варианта равновероятны,
  архитектура должна поддерживать оба одним кодом с самого начала.
- **Self-hosted закладываем на худший случай инфраструктуры**: у клиента может не быть
  Docker и/или интернета. Это исключает обязательные внешние зависимости (Redis,
  managed-сервисы) из ядра архитектуры.
- **Команда — соло-разработчик.** Каждая новая инфраструктурная единица (Redis, GPU-сервер,
  отдельный ML-пайплайн) — это реальная цена простоты и поддержки, не абстрактный риск.
- **Прогноз риска маловодья должен считаться строго на тех данных, что есть в системе** —
  без экстраполяции сверх исторических рядов, без ML на старте.
- **Автоматическая телеметрия с датчиков — в ближайших планах.** Схема данных должна
  быть готова принимать поток показаний, а не только ручной ввод из xlsx.
- **Автономные действия ИИ-агента на карте остаются только визуализацией** (highlight,
  фильтр) — агент не пишет в базу данных самостоятельно, человек решает, сохранять ли
  что-либо. Полноценный permission/approval-слой поэтому не входит в приоритет сейчас.
- **3D-рельеф — второстепенная фича**, не влияет на решение клиента о покупке.
- **Вход в реестр доверенного ПО РК — жёсткое условие сделки с первым клиентом.**
  Это означает: данные (включая обращения к ИИ-чату) не должны уходить на серверы за
  рубежом. Это отдельная категория от "self-hosted" — self-hosted сервер сам по себе НЕ
  решает эту проблему, если чат продолжает обращаться к DeepSeek/OpenAI по сети.
- Для локализации ИИ есть доступ к серверу/облаку в Казахстане, но без GPU — GPU нужно
  арендовать отдельно. Кандидат на модель — **Qwen**, уже протестирован локально, но
  не в проде до появления сервера.

## A. Мультитенантность и слой доступа к данным

**Проблема:** нужно поддерживать SaaS (общая платформа, много клиентов) и self-hosted
(изолированная копия у одного клиента) одним кодом, без форка.

**Решение:**

1. Доступ к данным переводится с прямых вызовов `@supabase/supabase-js` (`supabaseServer.ts`)
   на портируемый query-слой (рекомендация: **Drizzle ORM**) поверх обычной Postgres
   connection string. Supabase — это управляемый Postgres; отвязавшись от
   supabase-js-специфичных вызовов для доменных данных, приложение может подключаться
   к любому Postgres — управляемому (Supabase Cloud) или установленному локально у
   self-hosted клиента (нативная установка, без Docker) — без переписывания кода,
   только сменой строки подключения.
2. Схема мультитенантности:
   - `tenants` — одна строка на клиента. В self-hosted всегда ровно одна строка,
     зафиксированная в конфиге при установке (`TENANT_ID` в env). Код никогда не
     ветвится по признаку "это self-hosted" — просто в таблице `tenants` одна запись
     вместо многих.
   - `regions` — глобальный справочник регионов Казахстана, не принадлежит тенанту,
     сеется один раз.
   - `tenant_regions` — какие регионы доступны тенанту (self-hosted клиент — обычно
     1 регион; гипотетический национальный SaaS-клиент — несколько).
   - Все таблицы с доменными данными (`hydroposts`, `hydropost_readings`, ...) несут
     `tenant_id`.
3. Изоляция клиентов друг от друга — через Postgres RLS по `tenant_id`. Единообразно
   работает и в SaaS (реальная защита от утечки между клиентами), и в self-hosted
   (тривиально, но код не отличается).
4. **Резидентность данных:** желательно, но не жёстко для старта, чтобы данные физически
   лежали на сервере в Казахстане — это будущее требование реестра/законодательства РК.
   Решение из пункта 1 (портируемое подключение к Postgres) уже покрывает этот сценарий:
   начинаем на Supabase Cloud, при необходимости переключаемся на казахстанский сервер
   без переделки кода — меняется только строка подключения.
5. **Deployment mode:** env-флаг (`SAAS` | `SELF_HOSTED`) + единая функция определения
   тенанта из запроса — в SaaS через JWT/поддомен, в self-hosted — константа из конфига.

## B. Схема данных гидропостов и переход на телеметрию

**Проблема:** данные и история 28 постов зашиты в код; нужно принимать новые регионы и
(в ближайшей перспективе) автоматические показания с датчиков.

**Решение:** три таблицы вместо хардкод-массива:

1. **`regions`** — справочник регионов (см. блок A).
2. **`hydroposts`** — паспорт поста: код, название, район, водный объект, координаты,
   `tenant_id`, `region_id`, пороги статусов (danger/warning/normal cutoffs).
3. **`hydropost_readings`** — append-only временной ряд: `hydropost_id`, timestamp,
   уровень (см), источник (`manual_xlsx` | `telemetry`). Это целевая таблица под будущую
   автоматическую телеметрию: сейчас наполняется вручную (как сейчас, из xlsx), при
   подключении датчиков открывается отдельный приёмный API-эндпоинт, который просто
   добавляет строки в ту же таблицу — карта, чат и расчёт риска не требуют изменений.

**Следствия:**

- Статус поста (`danger`/`warning`/`normal`) перестаёт быть значением, которое
  поддерживается вручную, и вычисляется от последнего показания относительно порогов
  в `hydroposts`.
- Расчёт риска маловодья (сейчас `analyzeLowWaterRisk`, медиана исторических минимумов)
  переносится на `hydropost_readings` как есть — чистая математическая функция без ИИ
  внутри. ИИ-чат только объясняет словами уже посчитанный результат (как сейчас делает
  `detect_low_water_risk`), не участвует в самом расчёте — это гарантирует, что прогноз
  строго ограничен фактическими данными, без домысливания.
- Геослои (реки, озёра, сёла, районы — сейчас статичные JSON/GeoJSON в `public/`) в
  эту фазу **не переносятся** в базу — низкая срочность, нет требования телеметрии,
  можно оставить как per-region статические файлы до появления реальной проблемы с
  диском/размером деплоя (см. фазу 2).
- Готовится (но не подключается к реальному источнику) эндпоинт приёма показаний
  (`POST /api/ingest/readings`), чтобы при появлении датчиков не потребовалась повторная
  миграция схемы.

## C. Память чата и rate-limiting

**Проблема:** сессии чата и счётчики запросов живут в in-memory `Map` — теряются при
рестарте/на multi-instance деплое.

**Решение:** хранить в той же базе данных, что и доменные данные (две дополнительные
таблицы: история сообщений сессии, счётчик запросов с окном времени) — **не Redis**.

**Обоснование:** Redis — это ещё одна инфраструктурная единица, которую self-hosted
клиент (возможный сценарий: без Docker) должен был бы установить и поддерживать
отдельно от основной базы. При текущем масштабе (один регион, десятки одновременных
пользователей) Postgres обрабатывает эту нагрузку без проблем; лишний round-trip к базе
не заметен на этом уровне трафика. Redis остаётся опцией чисто для ускорения в будущем,
если нагрузка когда-нибудь реально этого потребует (фаза 2) — не архитектурная
необходимость сейчас.

## D. Локализация ИИ-агента (провайдер, комплаенс, архитектура)

**Это критический путь по срокам** — единственный пункт roadmap, требующий не только
кода, но и новой инфраструктуры (GPU), которой пока нет.

**Ключевое разграничение:** self-hosted развёртывание веб-приложения и "данные не уходят
за рубеж" — разные вещи. Даже если сайт крутится на сервере в акимате, чат при каждом
запросе отправляет текст вопроса и данные по гидропостам на `api.deepseek.com` (сервер
за рубежом) — это происходит независимо от того, где стоит сам веб-сервер. То же
касается голосовых функций через OpenAI.

**План (два параллельных потока):**

1. **Архитектурная подготовка (делаем сразу, не блокирует остальное):**
   Адрес и модель ИИ-провайдера выносятся в конфиг, а не зашиваются в код (сейчас это
   почти так и есть — вызов идёт по HTTP на фиксированный URL DeepSeek с форматом
   OpenAI-style function calling; большинство self-hosted инференс-серверов говорят на
   том же протоколе, так что переключение провайдера — это в основном смена URL/имени
   модели в настройках, не переписывание логики инструментов чата).

2. **Инфраструктурный трек (отдельная задача, идёт параллельно с блоками A-C):**
   - Аренда сервера/облака в Казахстане.
   - Аренда GPU там же (сейчас есть сервер без GPU — GPU арендуется отдельно).
   - Развёртывание Qwen (уже протестирован локально как кандидат) на этом сервере.
   - Проверка, что модель по качеству (русский язык, надёжность вызова инструментов)
     не хуже DeepSeek в проде.
   - Переключение боевого чата с DeepSeek на Qwen — **только после того, как сервер и
     модель реально готовы**. До этого момента DeepSeek остаётся рабочим вариантом,
     Qwen — протестированный, но не боевой кандидат.

3. **Голос (OpenAI STT/TTS):** заменить на открытые self-hostable инструменты (класс
   Whisper для распознавания, Piper/Coqui для озвучки) — работают на обычном CPU-сервере
   без GPU, не требуют отдельного дорогого трека. Более простая и дешёвая задача, чем
   замена LLM.

4. **Карта/погода/спутник (OpenFreeMap, Open-Meteo, Copernicus):** оставляем как есть.
   Это входящие запросы за общедоступными данными (карта, погода), а не отправка
   закрытых/государственных данных наружу — вероятно, вне периметра требования реестра.
   **Открытый риск:** нужно явно подтвердить у клиента/ответственного за реестр, что
   такие обращения к зарубежным публичным API не являются нарушением — это юридический
   вопрос, не технический, ответ не может быть дан из кода.

**Бизнес-правила вне строки system prompt:** отдельно от локализации, часть текущего
780-строчного system prompt в `route.ts` — это не инструкции для ИИ, а факты, которые
уже гарантированы кодом (например, цвет подсветки рек фиксирован в `AkmolaMap.tsx`,
не выбирается ИИ) — здесь ничего менять не требуется, это просто документирование
поведения кода для модели. Другая часть (например, "никогда не утверждай
upstream/downstream между постами") сейчас держится только как просьба к модели, но
де-факто подкреплена тем, что в данных попросту нет полей для описания такой связи —
это хороший паттерн (делать некорректное утверждение невозможным на уровне данных, а
не полагаться только на промпт) и его стоит сохранить при миграции system prompt на
генерацию из БД для новых регионов: список районов/рек/озёр в system prompt должен
собираться запросом к БД тенанта, а не быть захардкожен под Акмолинскую область — это
станет обязательным при появлении второго региона (см. фазу 1/2), а не опциональным
улучшением.

**Что сознательно не делаем сейчас:** полноценный permission/approval-слой для
автономных действий агента — подтверждено, что агент остаётся только визуализацией
(highlight/фильтр), не пишет в базу без участия человека. При этом стоит логировать
каждый вызов инструмента (не только финальный ответ) в уже существующую `activity_log`
— дёшево и полезно для отладки ("почему агент подсветил не ту реку"), но не требует
отдельной архитектуры прав доступа.

## E. Terrain-тайлы (3D-рельеф)

Подтверждено: второстепенная фича, не влияет на решение о покупке. **Ничего не меняем
сейчас.** Текущая схема (один локальный `.mbtiles`-файл на регион) уже корректно
работает для self-hosted (у клиента всегда один регион — один файл, ничего
не нужно переделывать). Проблема (дисковое пространство/размер деплоя) появится только
в SaaS при одновременном обслуживании нескольких регионов — откладываем до фазы 2,
когда это станет реальной, а не гипотетической проблемой.

## Фазированный план приоритетов

### Фаза 0 — сейчас, до сдачи первому клиенту (два параллельных трека)

**Трек "данные":**
1. Postgres + портируемый слой доступа к данным (Drizzle) вместо прямых вызовов
   supabase-js для доменных данных.
2. Схема `tenants` / `regions` / `tenant_regions` / `hydroposts` / `hydropost_readings`
   + RLS по `tenant_id`.
3. Миграция текущих 28 постов и истории из хардкод-массива в БД.
4. Заготовка эндпоинта приёма телеметрии (пока без реального источника данных).
5. Сессии чата и rate-limiting — в БД, in-memory `Map` убирается.
6. Автовычисление статуса поста от показаний и порогов.
7. Deployment-mode конфиг (SaaS/self-hosted) + единая функция определения тенанта.

**Трек "локализация ИИ" (параллельно, самое узкое место по срокам):**
1. Вынести адрес/модель ИИ-провайдера в конфиг (малая правка, не блокирует остальное).
2. Аренда сервера в Казахстане.
3. Аренда GPU, развёртывание Qwen, проверка качества (русский язык + вызов инструментов).
4. Переключение боевого чата с DeepSeek на Qwen — только когда сервер/модель готовы.
5. Замена OpenAI STT/TTS на self-hostable открытые инструменты.
6. Подтвердить у клиента статус обращений к картам/погоде/спутнику относительно
   требований реестра.

### Фаза 1 — после первого клиента, до второго региона

- Self-hosted-сценарий "нет Docker, нет интернета": при недоступности ИИ-провайдера
  чат автоматически переключается на уже существующий движок без ИИ (`aiMechanisms.ts`)
  — деградация, а не отказ функции.
- Перенос базы данных на казахстанский сервер, если ещё не сделано в фазе 0 (старт на
  Supabase Cloud допустим, если резидентность не была жёстким требованием с самого начала).
- Финализация RLS-политик и flow онбординга нового тенанта (сейчас ручное создание
  пользователя, нужен процесс для нового клиента/региона).
- System prompt генерируется из БД тенанта (список районов/рек/озёр), а не хардкодится
  под Акмолинскую область — обязательное условие для второго региона.
- Более развёрнутая статистика риска маловодья (перцентили, не только медиана) —
  по-прежнему без ML и без данных за пределами того, что фактически замерено.

### Фаза 2 — второй регион и далее, рост SaaS-нагрузки

- Перенос геослоёв (реки/озёра/сёла/районы) из статических файлов в БД/объектное
  хранилище — только если станет тесно на диске при нескольких регионах одновременно.
- Redis для сессий/rate-limiting — только если Postgres реально станет узким местом
  (маловероятно на обозримом масштабе).
- Terrain-тайлы → объектное хранилище — только для SaaS с несколькими регионами
  одновременно; self-hosted не меняется.
- ML-модель прогнозирования — только по явному запросу и финансированию конкретного
  клиента; не входит в архитектуру по умолчанию.

## Открытые вопросы (не решены в рамках этого документа)

- Юридическое подтверждение: считаются ли обращения к зарубежным публичным API
  (карты/погода/спутник) нарушением требований реестра доверенного ПО.
- Конкретный выбор self-hosted инференс-сервера (vLLM/Ollama/др.) и финальная
  валидация качества Qwen на реальных данных проекта — отдельная техническая задача,
  не решается в этом roadmap.
- Точный процесс регистрации в реестре доверенного ПО РК и его полный список
  технических требований, помимо "данные не уходят за рубеж".
